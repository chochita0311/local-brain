## Goal

- Make the real Claude CLI Session the authoritative Maintenance Session for an in-app Task Runner execution, and keep the Workstream Runner surface focused on starting and confirming that execution without a separate marker-creation workflow.

## Acceptance Contract

- The in-app Runner does not pass `--no-session-persistence`; Claude persists its normal Session while `--print` remains the non-interactive execution mode.
- The internal Run marker in the first user prompt links the persisted primary Claude Session to exactly one `maintenance_runs` row with `session_class=maintenance` and `index_policy=metadata_only`.
- Claude child Sessions inherit maintenance classification and metadata-only indexing through their persisted parent relation, remain outside work retrieval and statistics, and retain their directly observed Usage Records.
- Native Claude JSONL is the Session and Usage source of truth. Runner `stream.jsonl` remains a console/result artifact and never creates a synthetic Session or Usage Record.
- Dashboard and Workstream surfaces contain no standalone “실행 마커 생성” workflow or marker API dependency.
- The Workstream Runner displays the selected task's basic request, the exact CLI argument string used by the process, and the fact that the basic and optional extra requests are passed through stdin.
- The valid FEAT-0035 Session CHECK/FK/UNIQUE schema contract remains intact.

## Scope Boundary

- In:
  - native Claude Session persistence and post-run Claude-source synchronization
  - maintenance classification and Run linkage of the persisted primary Session
  - maintenance inheritance for persisted Claude child Sessions
  - removal of synthetic stream-backed Session/Usage producers and historical backfill
  - removal of marker creation UI, JavaScript, and API
  - exact shared Runner command preview on the Workstream screen
  - owner-policy, Data Model, PRD, and harness continuity updates
- Out:
  - removing `maintenance_runs`
  - changing the Session CHECK/FK/UNIQUE schema shape established by FEAT-0035
  - restoring the separately deferred compatible FK on `maintenance_runs.workstream_id`
  - reconstructing negligible historical test streams
  - changing Dashboard token/cost inclusion policy

## Contract Surfaces

- CLI arguments generated by `runner.py` and their Workstream preview.
- Internal prompt marker `[LOCALBRAIN_RUN: <id>] [MODE: maintenance]`.
- Claude JSONL ingestion, `sessions.maintenance_run_id`, parent linkage, and Usage Record ownership.
- `POST /api/workstreams/{workstream_id}/runs` remains the only in-app Run creation boundary.
- `POST /api/maintenance-runs` and its marker controls are removed.

## User-Visible Outcome

- A user sees one Task Runner form with its basic request and actual Claude command, starts the Run once, and does not have to create or copy a separate execution marker.

## Entry And Exit

- Entry point: Workstream Task Runner form.
- Exit or transition behavior: the existing Run status/console/result surface continues to report execution; native Claude Session ingestion links its Session and usage in the background.

## State Expectations

- Default: selected task, basic request, exact command, stdin explanation, and optional extra request are visible.
- Loading: existing Run submission state remains unchanged.
- Empty: no marker-specific empty state remains.
- Error: existing Run error state remains; ingestion failure does not fabricate stream-backed usage.
- Success: the persisted native Session is linked and the existing Run result remains available.

## Dependencies

- FEAT-0035's compatible Session-table CHECK/FK/UNIQUE repair remains the schema prerequisite.
- FEAT-0015 parent/subsession contract supplies the child relation used for maintenance inheritance.
- FEAT-0034 supplies the canonical Usage Record terminology and native Claude usage normalizer.

## Likely Affected Surfaces

- `src/localbrain/runner.py`, `src/localbrain/ingest/scanner.py`, `src/localbrain/ingest/claude.py`, `src/localbrain/usage.py`, `src/localbrain/db.py`
- `src/localbrain/main.py`, Dashboard and Workstream templates, application JavaScript and styles
- Task Runner, Session/Usage, privacy, architecture, and Data Model owner documents

## Pass Or Fail Checks

- Pass if the executed and displayed command share one producer and neither contains `--no-session-persistence`.
- Pass if a persisted primary marker Session links to its Run and a child Session becomes maintenance/metadata-only without taking the Run's unique FK.
- Pass if native Session usage remains Dashboard-eligible while both primary and child maintenance Sessions stay outside work-facing consumers.
- Pass if no stream-backed synthetic Session or Usage producer, startup backfill, marker UI, or marker API remains.
- Pass if the Workstream command is readable without breaking narrow-screen containment and all existing Run submission behavior remains intact.
- Fail on duplicate Session sources, usage double counting, child leakage into work consumers, UI/API marker residue, command-preview drift, or loss of the existing schema constraints.

## Regression Surfaces

- Run lifecycle, cancellation, artifacts, structured result parsing, and Suggestion provenance.
- Ordinary Claude/Codex ingestion, parent reconciliation, Usage pricing, Dashboard totals, Session inventory, and Workstream retrieval.
- Schema presentation and compatible Session migration parity.
