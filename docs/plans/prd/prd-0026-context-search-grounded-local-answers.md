## Request Summary

Sessions Dashboard 아래에 `Context Search`라는 가칭의 독립 탐색 메뉴를 두고, 처음에는 질문 입력 중심 화면, 질문 후에는 질문과 답변을 중심으로 보여준다. 내 Local Context와 Google Drive에서 받아둔 다른 사람의 폴더를 함께 찾아 업무·사람·주제에 관한 질문에 답하는 기능을 검토한다.

사용자는 로컬 Qwen 4B·8B의 역할, 자료를 질문에 제공하는 방식, 임베딩·색인 준비와 모델 학습의 차이를 이해한 뒤 범위를 확정하려 한다. 초기 논의는 기존 Drive 전송 승인과 별개였다. 아래 승인된 첫 전달 범위는 새 사용자 실행 지시에 따른다.

후속 질문에서는 4B가 선택한 폴더의 목록·텍스트 검색·파일 읽기 도구를 사용해 자료를 탐색하고, 임베딩 색인은 나중에 도입하는 방식도 가능한지 제기했다. 직접 도구 탐색을 초기 후보로 검토하며, 임베딩 선행을 필수 조건으로 두지 않는다. 이 가능성 질문 자체는 구현 승인이 아니었으며, 이후 명시적인 실행 지시가 아래 범위를 승인했다.

## Approved First Delivery

- 원본 공개 모델은 기존 사용자 공용 Hugging Face Hub 캐시를 재사용하며 중복 복사·이동·정리하지 않는다. 앱 등록 manifest는 기존 `<data>/models/`, 앱 전용 실행/컴파일 캐시는 `<cache>/context-search/`에 둔다. 개인 자료나 대화를 Hub에 쓰지 않는다. 실제 사용자 절대 경로는 문서 기본값에 넣지 않는다.
- 기존에 설치한 Qwen3-4B와 Qwen3-8B를 화면에서 선택한다. 모델 설치/검증은 설정의 검색 모델에 추가하며 공용 캐시가 완전하면 재다운로드하지 않는다. 공개 자산 설치는 명시적인 설정 동작이며 질의가 네트워크 다운로드를 시작하지 않는다.
- 첫 검색은 임베딩 없이 허용된 내 Local Context와 이미 받은 Drive 폴더의 읽기전용 목록·문자열 검색·부분 읽기다. 기존 색인 제외 규칙을 전역 완화하지 않는다. 파일 기반 Context는 읽을 수 있는 텍스트를 직접 읽고, Notes 등 정규화 문서는 기존 읽기 가능한 수집 본문을 사용한다. 지원하지 않는 바이너리/읽기 제한은 명시해 부분 결과로 다룬다.
- 같은 화면에서 이어 묻되 질문·답변·도구 내용은 요청/브라우저 메모리에만 둔다. DB 테이블, 대화 파일, localStorage/sessionStorage/IndexedDB 저장을 추가하지 않는다. 앱 다른 화면/설정으로 이동하거나 브라우저 탭이 숨겨지면 대화와 미완료 요청을 지운다. 돌아왔을 때나 새로고침/뒤로 가기 복원도 빈 대화로 시작한다. 저장 기능은 후속 별도 설계다.
- 화면은 Sessions Dashboard 아래 Context Search, 중앙 입력과 이어지는 Q/A, 모델 선택·중단·작은 근거 펼침으로 제한한다. 모델은 한 번에 하나만 로드하며 전환/취소/종료를 관리한다. 모델 추론의 네트워크 차단은 별도 worker에 적용해 웹 서버·Drive에 영향을 주지 않는다.
- 모델/근거가 준비되지 않았거나 한도·실행 오류가 있으면 원인을 설명하고 입력/재시도 경로를 유지한다. 임의 shell, 원문 쓰기, 외부 AI, 답변 영속화와 임베딩 추가는 이번 범위가 아니다.

## Product Intent

자료가 누구 폴더의 어떤 파일에 있는지 몰라도 질문으로 관련 내용을 찾고 이해한다. 대표 질문은 특정 팀 구성원이 주로 어떤 일을 하는지, 특정 업무나 문제를 누구에게 물으면 좋을지다. 로컬에 보유한 자료에서 확인할 수 있는 사실과 근거로부터의 추천을 구별한다.

사용자가 매 질문마다 폴더를 첨부하거나 문서를 미리 요약·학습시킬 필요가 없는 흐름을 목표로 한다. 앱이 허용된 자료 탐색과 근거 제공을 담당하며, 사전 색인을 사용하는 구성에서는 그 준비도 담당한다. 질문과 답변이 중심이며, 검증이나 준비 상태가 필요할 때 이해 가능한 정도로 드러난다.

앱이 원문에서 검색 단위를 만들고 의미 벡터를 계산하는 **색인 준비**와, 모델 가중치를 바꾸는 **학습**은 다르다. 두 가지 근거 탐색 구성을 함께 검토한다. **직접 도구 탐색**은 생성 모델이 선택 폴더에서 목록·텍스트 검색·부분 읽기를 요청하고 앱이 결과를 반환하며 필요한 탐색을 이어가는 방식이다. 이 구성에는 사전 임베딩이나 전체 텍스트 색인이 필수로 들어가지 않는다. **색인 보조 검색**은 키워드/벡터 색인에서 관련 구절을 먼저 찾는 방식이다. 두 구성 모두 찾아낸 자료를 근거로 답할 수 있으며, 직접 탐색에 임베딩 검색을 나중에 보조 도구로 추가할 수도 있다. 기존 임베딩 검색의 존재만으로 첫 버전의 선행 조건을 고정하지 않는다.

생성 모델에 폴더 경로와 “찾아봐”라는 문장만 전달해도 파일을 읽는다고 가정하지 않는다. 직접 탐색에서는 모델이 어디를 어떻게 찾을지 요청하고 실제 파일 접근은 앱 도구가 수행한다. 반환한 목록·검색 결과·필요한 문서 구간이 다음 모델 입력이 된다. 전체 폴더의 크기와 모델 입력의 토큰 한도는 별개이며, 8B라는 모델 크기만으로 더 많은 자료를 한 번에 읽을 수 있다고 약속하지 않는다.

## Confirmed Scope

1. **별도 메뉴:** Sessions Dashboard 아래의 독립 메뉴, `Context Search` 가칭. 최종 명칭은 열어둔다.
2. **질문 중심 진입:** 처음에는 질문을 입력할 수 있는 간결한 화면. 질문 후에는 질문과 답변이 주된 내용이다. ChatGPT 첫 화면은 상호작용의 참고이며 브랜드나 다른 앱 전체 UI를 복제하는 요구가 아니다.
3. **함께 찾는 자료:** Google Drive로 받아 로컬에 있는 타인의 폴더와 내 Local Context를 함께 검색한다. 등록·활성·가독성 계약은 Approved First Delivery와 OP-02에서 확정됐으며, 개별 검색 폴더 선택 UI는 후속 범위다.
4. **업무와 문의 대상 탐색:** 업무 설명, 문서에 나타난 사람/역할, 관련 주제와 질문할 후보를 찾는 것이 주요 사용 사례다.
5. **로컬 모델 방향:** 질문 해석·근거 정리·답변 작성에 로컬 생성 모델을 활용하는 방향이다. 작성 초기 Qwen 4B·8B는 검토 대상이었으며, 승인된 첫 전달에서는 설치된 Qwen3-4B/8B와 기존 pinned 실행 경로를 사용한다. 기기별 메모리·지연과 넓은 질문 품질은 별도 검증이다.
6. **실행 승인:** 사용자가 공용 모델/앱 캐시 분리, 4B·8B 선택/설치 UI와 휘발성 대화를 지정하고 진행을 요청했다. 아래 범위 안에서 Feature 작성부터 구현·검증까지 진행한다. 답변 저장 설계는 별도다.

## Earlier Proposals And Retrieval Rationale

아래는 승인 전 검토한 제안의 근거다. 현재 첫 전달 선택은 Approved First Delivery가 소유하며 저장/추가 색인 등 후속 선택은 승인하지 않는다.

- 첫 화면은 한 개 질문 입력창과 짧은 안내/예시 질문 정도로 구성한다. 질문 후에도 입력, 질문, 답변의 간결한 흐름을 유지한다. 새 대시보드·조직도·벡터 관리 화면은 제안하지 않는다.
- 답변에는 필요할 때 열 수 있는 간결한 근거 파일/구간 링크를 제공한다. “질문과 답만”이라는 표현과 출처 표시의 조합은 OP-03에서 확인한다.
- 초기 후보는 **로컬 생성 모델 + 선택 폴더의 읽기전용 목록/텍스트 검색/부분 읽기 도구**다. 예를 들어 사용자가 지정한 여러 폴더에서 특정 기술의 사용 방식을 묻는다면, 모델이 관련 검색어와 파일을 고르고 내용을 추가로 읽으며 근거 답변을 작성한다. 모델 미세학습이나 전체 폴더의 사전 임베딩 완료를 시작 조건으로 두지 않는다.
- Qwen3-4B/8B의 도구 요청 정확도, 잘못된 검색 후 회복, 넓은 질문의 자료 누락과 반복 지연을 실제로 비교한다. 사용자의 질문과 대상 폴더가 분명한 경우 직접 탐색을 우선 후보로 두되, 모든 질문에 더 빠르거나 정확하다고 가정하지 않는다. 기존 Qwen3-Embedding-0.6B/키워드 색인은 자료 범위가 커지거나 의미상 관련 구간을 찾기 어려울 때 보조 검색 선택지다. 재정렬 모델, 양자화와 별도 inference engine은 현재 필수 구성으로 추가하지 않는다.
- 직접 탐색은 현재 로컬 사본을 대상으로 하며, 추가·수정·이동·삭제 및 읽기 도중 변경을 근거 관측에 반영하는 계약이 필요하다. 색인을 도입한 경우에는 그 검색 준비를 증분 갱신한다. 원본 파일 전송과 검색용 본문 준비는 책임을 구분하며, 새 검색 지원 형식이 Drive 전체 원본 전송을 필터링하지 않는다.
- 넓은 질문은 여러 문서/출처에서 확인해야 한다. 소수의 유사 구간만으로 전체 팀의 모든 업무를 파악한 것처럼 표시하지 않는다. 질문에 따라 근거를 확장/집계하는 필요와 응답 한계는 평가 대상으로 둔다.

## Excluded Scope

명시적으로 요청되지 않았으며 이번 초기 경계에 자동으로 포함하지 않는 범위다. 추가 요청 시 다시 검토한다.

- 기존 Drive 인증·원본 전송·삭제·자동 주기 계약의 재설계나 새 외부 업로드.
- 사용자 자료를 외부 AI로 전송하는 기본 동작, 내부 문서별 모델 재학습, 개인 문서를 제품 가중치/배포물에 포함하는 방식.
- 기존 Session 전체를 이 화면의 자료로 자동 추가하는 것. 이번 선택은 받은 폴더와 내 Local Context다.
- 폴더명으로 사람/팀/직책/담당자를 확정하거나 회사 전체의 정식 조직도·인사/역할 디렉터리를 구축하는 것.
- 답변을 문서에 쓰기, 원문 수정, 다른 사람에게 메시지 보내기, 업무 배정이나 자동 관계 확정.
- 대화 목록·공유·장기 기억·음성·파일 업로드 도구·무제한 자율 실행을 처음부터 당연한 채팅 기능으로 추가하는 것. 선택 자료의 읽기전용 목록·검색·읽기는 직접 탐색안에 포함해 검토한다. 필요한 대화 지속성은 OP-04에서 별도로 정한다.

## Constraints

- 원본, 수신 사본, 검색 파생 데이터와 생성 답변을 구별한다. 기존 출처/원문 위치와 갱신 관측을 보존하고, 정상 동기화·색인 완료와 단순 파일 존재를 같은 상태로 표시하지 않는다.
- 수신 게시자 폴더는 출처 식별자다. 폴더 소유자, 문서 작성자, 본문에서 언급된 사람, 실제 담당자/문의 대상은 서로 다를 수 있다. 문서에 명시된 사실과 추천·추정을 구별한다. 동일 이름/상충 문서/시점 불명이 있으면 근거와 한계를 설명한다.
- 원격 접근 실패나 동기화 중단이 로컬 사본을 삭제한다는 새 계약을 만들지 않는다. 이미 보존한 로컬 자료의 이용은 기존 공유/사본 원칙을 따른다. 검색 포함과 최신성 표시는 OP-02에서 정한다.
- 등록되지 않은 런타임 데이터, 토큰, 로그, 다른 사적 자료를 corpus에 섞지 않는다. 선택된 수신 자료를 다루는 명시적인 source 경계가 필요하다. 검색을 위해 기존 일반 Context 화면에 모든 수신 폴더를 자동 등록하는 것으로 간주하지 않는다.
- 직접 탐색 도구는 사용자가 허용한 수신 폴더와 Local Context의 읽기 범위에 한정한다. 모델은 도구 호출을 제안하며 앱이 경로·조회 범위·읽을 구간을 적용하고 결과를 돌려준다. 목록/검색/읽기 연결이 임의 시스템 명령이나 쓰기/외부 전송 권한을 의미하지 않는다. 필요한 파일 구간을 단계적으로 읽으며, 반복이 끝나지 않거나 자료 일부만 확인한 경우를 전체 확인처럼 답하지 않는다.
- 지원하지 않거나 읽지 못한 형식/본문이 있으면 준비 범위를 설명한다. “폴더를 받음”이 “모든 파일의 내용을 검색·답변 가능”을 의미하지 않는다. 첫 전달의 UTF 텍스트와 적격 수집 본문 범위는 Approved First Delivery에서 확정됐고, 추가 형식 변환은 후속이다.
- 근거가 부족한 질문은 확인 불가/부분 답변으로 다룬다. 추천이나 생성 문장 자체를 검증된 회사 사실로 저장하거나 출처를 만들어내지 않는다. 문서 안의 명령문을 시스템 지시나 외부 작업 권한으로 취급하지 않는다.
- 입력 한도와 메모리를 고려해 필요한 구간을 제공한다. 기존 생성 코드는 CPU float32/가속기 bfloat16 기반으로, 4-bit 배포나 메모리/응답 목표가 이미 검증됐다고 표시하지 않는다. 4B/8B 선택은 실제 실행 환경과 질문 품질 비교가 필요하다.
- 기존 앱 shell/디자인 토큰/접근성과 320px 탐색성을 따른다. 구현을 승인할 때 Fullstack profile과 corpus/검색/생성/화면 lanes, contract/design/functional/interaction 평가가 필요하다.
- 개인 이름, 조직, 실제 폴더명·경로·ID와 사적 질문/본문/평가 기록은 공통 개발 문서·테스트·스크린샷에 넣지 않는다. 공개 예시는 합성 자료만 사용한다.

## Acceptance Envelope

승인 범위의 상위 수용 조건이다. 구체적인 Feature 계약은 Approved First Delivery 안에서 고정한다.

1. Sessions Dashboard 아래 독립 메뉴로 진입하고, 질문 입력과 질문/답변의 간결한 흐름을 사용할 수 있다.
2. 허용된 받은 폴더와 내 Local Context를 함께 찾되, 기존 Session/런타임 제외와 실제 자료 범위를 보존한다. 직접 탐색안은 사전 임베딩 완료 없이 목록·검색·읽기로 근거를 찾을 수 있어야 하며, 확인하지 못한 형식·범위나 선택적 색인 준비 상태를 전체 검색 완료처럼 표시하지 않는다.
3. 자료에 실제로 존재하는 사람·업무·문의 후보에 관해 한국어로 답하고, 사실/추정/근거 부족을 구별하며 원문 근거로 확인할 수 있다. 폴더 이름만으로 사람/소속을 꾸며내지 않는다.
4. 자료 변경이 새 질문에 반영되며, 오래된/충돌하는 근거와 부분 탐색·준비 범위를 현재 확정 사실처럼 답하지 않는다. 원본 동기화와 선택적 검색 파생 데이터는 별도 책임을 유지한다.
5. 모델·자료 탐색·선택적 색인 준비의 실패나 취소 시 사용자 입력과 복구 방법이 유지되고, 외부 AI 호출이나 원문 수정으로 조용히 대체하지 않는다.
6. 모델 선택은 같은 corpus/질문/근거 조건에서 근거 적합성, 인용 일치, 문의 후보의 뒷받침, 확인 불가 응답, 지연과 자원 사용을 구분해 검토한다. 모델 크기나 합성 테스트만으로 모든 기기·자료의 품질을 보장하지 않는다.

## Candidate Features

아래는 승인 전 후보 분해다. 승인된 실제 실행은 Features0151–0153이 소유하며, 저장 기능이나 임베딩 후속 범위를 추가하지 않는다.

- **공동 corpus·출처·갱신 계약 — foundation:** 받은 자료와 내 Context의 식별/포함/원문 근거/갱신·제외·최신성 의미를 고정한다.
- **두 자료 영역의 읽기전용 탐색과 근거 검색 — product:** 허용된 자료의 목록·텍스트 검색·부분 읽기를 모델에 연결하고 탐색 범위/부분 결과를 확인할 수 있게 한다. 선택적 색인 검색은 첫 방식과의 경계 검토 후 분리할 수 있다.
- **로컬 근거 답변 실행 — product:** 선택 모델이 근거를 읽어 답하고 출처/추정/근거 부족을 유지하는 결과를 제공한다.
- **Context Search 진입과 질문/답변 화면 — product/fullstack:** 승인된 검색·생성 계약을 사용하는 최소 화면을 기존 앱 shell 안에 제공한다.
