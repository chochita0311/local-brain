# Maintenance Task Runner

## Purpose

The Task Runner starts a local maintenance process. Existing Workstream resource organization, checkpoint drafting, and priority review use Claude. External synchronization may select Claude or Codex under one source-neutral contract. LocalBrain owns the durable Run record and one linked metadata-only Maintenance Session; maintenance execution must never become an ordinary indexed work Session.

## Execution Contract

- Each Run starts a new top-level runner process rather than resuming an ordinary work Session.
- Existing Workstream tasks keep the user's home directory as their default working directory so approved local sources can be discovered beyond an already linked project. External synchronization runs inside its private Run artifact directory and receives no unrelated local corpus.
- Existing Claude tasks use `--print --output-format stream-json --verbose --permission-mode plan --json-schema`. They do not pass `--no-session-persistence`; Claude's persisted native JSONL is their Session and Usage source.
- Preparing an in-app Run creates only the `maintenance_runs` ledger row and private artifact paths. The internal header in the stdin prompt lets the next Claude-source sync classify and uniquely link the persisted primary Session as `maintenance`, `primary`, and `metadata_only`.
- The permission mode is read-only planning.
- FastAPI launches the CLI as a background child process so request handling remains non-blocking.
- The top-level agent may use subagents only when broader exploration is necessary.
- The Workstream Run form displays the selected task's base request, the exact CLI argument string generated by the same command builder used for execution, and that the base request plus optional `추가 요청` are passed through stdin. The extra text is appended rather than replacing the base request.
- Cancellation, completion, failure, and observed tool usage are persisted in `maintenance_runs`.
- Every terminal path triggers synchronization for the selected native Claude or Codex source. Native message usage is normalized through the ordinary source producer; the Runner stream never creates a second Usage Record.
- Common Run state includes `queued`, `running`, `completed`, `partial`, `failed`, `cancelled`, and `interrupted`; `cancelling` is the transient stop request.
- The Run Console polls live status and output, exposes artifacts, and supports cancellation without blocking FastAPI requests.

`LOCALBRAIN_CLAUDE_BIN` and `LOCALBRAIN_CODEX_BIN` may select their respective executable. `LOCALBRAIN_RUN_ID` is provided to the child process for Run attribution.

## External Synchronization

`external_source_sync` uses `localbrain.external-sync-manifest.v1` for both runner kinds. Detailed selected locators, metadata/content/hierarchy coverage, known remote evidence, field allowlists, logical operations, and the hard preparation-time call budget remain in the private manifest. `external_sync_runs` stores only the source-neutral query projection.

Preparation requires every selected target's enabled Source Instance to have one current FEAT-0044 capability observation. A single-source Run keeps the original manifest source shape. A mixed-source Run keeps the aggregate source identity nullable and carries an authorized `source_instance_id` on each target; one target can never switch source after preparation. Every request is a logical operation; `authorize_external_read` resolves and validates the immutable provider dispatch before a Run is queued. A manifest or model cannot provide a tool name.

Execution requires an injected host-side read executor. That executor receives only approved dispatch descriptors and returns bounded evidence. LocalBrain validates outcome, source identity, metadata, eligible content, remote version/update evidence, and safe errors; it computes content hashes locally. Tool-call accounting retains request ID, target ID, logical operation, resolved tool name, and outcome, but excludes arguments and returned content.

The selected model sees only the validated local manifest and evidence:

- Claude receives no tools and a strict empty MCP configuration; validated input is supplied through stdin.
- Codex uses `exec`, a custom permission profile that grants read access only to minimal runtime paths and the Run root while disabling network access, ignores user configuration and rules, and retains its native Session by omitting `--ephemeral`.

Both return `localbrain.external-sync-model-result.v1`, which contains only Run identity and a bounded summary. LocalBrain assembles `localbrain.external-sync-result.v1` from host-validated facts plus that presentation summary. Model prose cannot author or replace source facts.

All-success target outcomes finish `completed`; mixed success and failure finishes `partial`; no successful target, absent executor, launch failure, or invalid model output finishes `failed`. Cancel and restart behavior remains source-neutral and never applies or deletes prior external Item state. For an explicit Atlassian refresh manifest, the host validates the complete result and atomically applies FEAT-0046 Item state/content before committing the same terminal Run transaction. Invalid target, source, locator, or result mappings leave both the last-known Item state and terminal success unset.

Atlassian refresh preparation is a product-level specialization of this contract. Its local preview makes no external or model call, supports Item, Space, Thread, Workstream, and all-known scopes, and hard-caps the submitted selection at 20 calculated reads. One mixed-Source user action remains one maintenance Run. Jira Space scope contains known selected Items only. Confluence catalog expansion is a separately selected request for one page of at most 200 regular Page identities; Page bodies are not fetched by that catalog request.

## Local Retrieval First

Before Claude starts, LocalBrain performs deterministic SQLite and FTS5 retrieval without an AI call.

- The context manifest contains Session, Document, Project, local-path, and external-reference candidates.
- Session candidates are restricted to `session_class=work` and `session_role=primary`. Maintenance Sessions and subsessions never contribute candidate counts, evidence, fingerprints, manifests, or generated Suggestions, even when they already have a Workstream or Thread link. Their content is not merged into an eligible parent.
- The current Run, earlier Claude Runs, and any subagents used by those Runs remain execution activity. They must not be proposed back as new Workstream resources.
- Candidate resources and matching evidence have relevance criteria but no hard count cap.
- A resource is represented once even when it is relevant to multiple Threads.
- Many-to-many Thread assignments and evidence IDs are stored separately.
- Full evidence is written as one deduplicated file per candidate and opened only when needed.
- An unchanged candidate fingerprint carries forward the previous structured result so Claude can avoid repeated investigation. This `previous_analysis` cache is separate from candidate resources and evidence; it does not make the previous Run or its subagents retrieval inputs.

Claude should use external MCP tools only to fill gaps that remain after local evidence review.

## MCP Budget

`LOCALBRAIN_MCP_CALL_BUDGET` sets the advisory MCP call budget for one Run and defaults to `20`.

The current Claude CLI can cap monetary spend but does not expose a hard MCP call-count limit. LocalBrain therefore:

- states the budget in the prompt
- records observed `mcp__*` stream events
- reports budget overruns after calls occur

This is a soft policy, not strict enforcement. A future MCP proxy or broker boundary is required for a hard call-count limit.

## Persistence

Run metadata is stored in `maintenance_runs`; external synchronization adds exactly one `external_sync_runs` query projection. The selected runner's native Session and Usage Records are normalized into `sessions` and `usage_records` inside `localbrain.db`. Artifacts are stored under:

```text
~/Library/Application Support/LocalBrain/runs/<run-id>/
```

Artifacts include the generated prompt, manifest and fingerprints, operational stream output, structured result, and per-resource or provider evidence. The stream drives result parsing but is not a Session or Usage rebuild source. Native Claude or Codex JSONL remains authoritative. Artifacts are private runtime data and must remain outside Git.

## Review And Mutation Rules

- Structured Resource and Checkpoint candidates are saved as pending Suggestions.
- A Resource candidate targets the most relevant Thread by default.
- A Workstream-level target is reserved for evidence genuinely shared by multiple Threads.
- Accepting a Resource materializes its local path or external reference and then creates the link.
- Accepting a Checkpoint creates a versioned confirmed state with the current resource snapshot.
- Rejected Suggestions remain visible and can be restored.
- Refresh replaces eligible pending Claude Run Suggestions only after a new structured result succeeds.
- Accepted and rejected decisions survive refresh.
- A failed or cancelled Run must not clear the review queue or silently mutate Workstream organization.

Only explicit user acceptance may change Workstream organization.

## Index Exclusion

Maintenance prompt headers identify housekeeping activity:

```text
[LOCALBRAIN_RUN: lb-<12 hex characters>]
[MODE: maintenance]
```

Sessions beginning with this exact internal header retain source metadata but are excluded from activity events, full-text search, workflow statistics, and the Sessions Dashboard primary-work Session denominator. A registered Run ID populates the unique Run FK; an unregistered header remains maintenance with no physical Run relation. Claude and Codex child Sessions inherit maintenance classification and metadata-only indexing from a linked maintenance parent while retaining their own directly observed Usage Records; only the primary holds the unique Run FK. Direct Maintenance Usage Records remain eligible for token and estimated-cost totals. Run artifacts remain outside ordinary Session and Local Context ingestion.
